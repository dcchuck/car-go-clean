# The owner’s tour of car-go-clean v0.4

This is the product-level walkthrough: what the program considers trustworthy,
what it will clean, how the daemon behaves, and how a release reaches users.
For field-by-field details, use the
[configuration reference](configuration.md). For release operations, use
[Releasing car-go-clean](releasing.md).

## If you remember only five things

1. **Discovery history is not permission.** Cleanup needs a current policy,
   discovery generation, observation, and final safety check.
2. **The normal manual flow is review, then execute.**
   `run --dry-run --all` creates a bounded plan; `run --review ID` can only
   narrow that plan.
3. **Protected storage is out by default.** Cargo/Rustup caches, container
   storage, macOS `Library`, OrbStack, Docker Desktop, and similar roots are
   excluded. Managed storage needs both configuration admission and explicit
   plan-time approval.
4. **The daemon is opt-in.** Installing the binary does not install a service.
   `service stop` disables it persistently; `service start` re-enables it.
5. **Outcomes are stable.** `0` means complete, `2` means valid but incomplete,
   and `1` means failed. A macOS privacy denial is commonly `2`, not permission
   to ignore the missing coverage.

## 1. What car-go-clean is now

At its center, car-go-clean is a conservative scheduler for one ordinary Rust
operation:

```text
cargo clean --target-dir <project>/target
```

It runs that command from the project directory and removes
`CARGO_TARGET_DIR` from Cargo’s environment. It does not recursively delete
source checkouts, package-manager caches, or arbitrary directories. The
cleanup target is the direct, non-symlink `target/` beneath a discovered Rust
project.

Around that operation are five product layers:

| Layer | Job |
| --- | --- |
| Discovery | Find in-scope Rust projects and linked Git worktrees. |
| Authority | Bind those observations to the exact current policy and scan generation. |
| Safety | Reject recent, active, unreadable, replaced, excluded, or protected targets. |
| Operation | Offer reviewed one-shot cleanup, dynamic cleanup, or scheduled daemon cleanup. |
| Audit | Record attempts, failures, recovered bytes, diagnostics, and scheduler state. |

The CLI and daemon share the same discovery, authority, safety, Cargo, and
accounting code. The daemon is not a separate “fast path.”

The important v0.4 change is the distinction between **knowing that a path was
once a Rust project** and **having current authority to clean it**. Database
history is useful for reporting; it is never sufficient by itself to reach
Cargo.

## 2. What it finds

### Discovery inputs

car-go-clean has two kinds of configured origin:

- `scan_dirs` are recursively searched. The default is the current user’s
  home directory.
- `project_dirs` name individual Rust projects that should be considered
  explicitly.

A discovery candidate is a directory containing `Cargo.toml`. Before cleanup,
the manifest must pass the stricter direct, non-symlink regular-file check.
The scanner does not traverse symlinked directories. It prunes `target`,
respects `.gitignore` rules, and applies the effective exclusion set before
admitting a project.

Each configured origin gets its own completion result. That matters: one
unreadable origin does not turn the paths found elsewhere into fiction, but it
does make overall coverage incomplete.

### Git worktrees

When a primary checkout has a real `.git/` directory, car-go-clean asks Git
for its linked worktrees. A linked worktree is admitted only when it is:

- inside a configured scan root, or exactly an explicit project;
- not excluded;
- canonicalizable and observable; and
- still associated with the primary Git checkout.

This catches large `target/` directories in linked worktrees even when normal
directory traversal or ignore rules would not reach them.

A failed Git worktree enumeration is durable safety information. The affected
primary and saved linked paths remain blocked until a later successful
enumeration reconciles them. Untrusted legacy failure state fails even more
conservatively.

### Exclusions and protected storage

The editable discovery defaults always include `.git` and `node_modules`.
They also exclude package-manager, VM, trash, cache, and container roots:

- All supported hosts: `.cargo`, `.rustup`, `.cache`,
  `.bun/install/cache`, `go/pkg/mod`, `.colima`, `.lima`, and
  `.local/share/containers`.
- macOS: `Library`, `.Trash`, and `OrbStack`.
- Linux: `.local/share/docker`, `.docker/desktop`,
  `.local/share/rancher-desktop`, and `.local/share/Trash`.

Environment-defined roots such as `CARGO_HOME`, `RUSTUP_HOME`,
`XDG_CACHE_HOME`, `XDG_DATA_HOME`, `GOMODCACHE`, `BUN_INSTALL`,
`COLIMA_HOME`, and `LIMA_HOME` also participate in protected-root policy.

Relative exclusions remain lexical and are never canonicalized; they do not
need to exist as paths. Only absolute exclusions receive a canonical form.
Most machines do not have every absolute default root, so `NotFound` is
normal. Any other absolute-exclusion canonicalization error—for example an
existing but unreadable path—blocks policy construction and cleanup
authority.

Removing an exclusion does not automatically authorize protected storage.
Managed cache or container cleanup needs both:

1. configuration that admits the path into discovery; and
2. `run --dry-run --include-managed-cache` when the review is created.

## 3. What grants cleanup authority

Cleanup authority is a chain. Breaking any link stops the path before Cargo.

### Policy hash

The policy hash is a versioned SHA-256 fingerprint of an enumerated tuple:

- canonical scan roots;
- canonical explicit projects;
- lexical and canonical exclusions;
- protected roots, their kinds, and their provenance;
- target quiet period;
- scan interval; and
- the config source path.

Changing one of these values changes the policy. The hash is not a vague
checksum of “relevant settings”; its inputs are explicitly versioned.

### Discovery generation and origin

A scan attempt reconciles a generation under one policy hash, even when one
origin is incomplete. The generation records:

- every configured origin and whether it completed;
- each project observed through that origin;
- project and target filesystem identity; and
- the current boot session.

Only an observation authorized by the current generation can become
cleanable. Overlapping origins do not multiply authority.

`run --no-scan` reuses a current matching generation. It does not elevate old
project rows into authority.

### Observation and identity

Project and target device/inode identity are change detectors. They answer
“is this still the object we observed?” within a boot session; they are not
permanent capability tokens.

After a reboot, the boot-session change forces physical re-observation before
the identity can be trusted again. A path replacement, target replacement,
canonical-path change, or same-device violation becomes a skip.

### Review plan

Every dry run with a valid current generation persists a plan containing:

- policy hash;
- discovery generation;
- creation and expiry times;
- candidate bytes; and
- the exact reviewed target decisions and identities.

A plan expires after 30 minutes. At most the newest 20 current plans are
retained. Policy and generation changes invalidate old plans.

Execution can remove newly unsafe targets. It can never add a target that was
not in the persisted review.

## 4. A target’s lifecycle

One target moves through these boundaries:

1. **Discover.** A scan observes a project under a configured, non-excluded
   origin and records a generation.
2. **Review.** car-go-clean checks the direct manifest and target, measures
   bytes, classifies storage, samples activity, evaluates scan errors, checks
   quiet time, and binds identity.
3. **Persist or select.** A dry run saves the exact decision in a review plan.
   A dynamic run selects the fresh reviewed set in memory.
4. **Revalidate.** Immediately before cleanup, car-go-clean rechecks policy,
   canonical paths, scope, exclusions, storage class, activity, errors,
   quiet time, same-device placement, and filesystem identity.
5. **Invoke Cargo.** Only then does it emit a target event and run
   `cargo clean --target-dir <direct target>`.
6. **Account.** It measures the remaining target, records the Cargo exit and a
   bounded stderr excerpt, updates run totals, and records any error.

The final revalidation substantially narrows path-replacement races. It cannot
eliminate the residual time between the last user-space check and Cargo
opening the project.

## 5. Using it once

### Recommended: reviewed cleanup

```sh
car-go-clean run --dry-run --all
car-go-clean run --review REVIEW_ID
```

The first command scans, applies the safety policy, invokes no Cargo command,
and prints the review ID, policy hash, generation, expiry, and candidate
bytes. `--all` expands only the displayed cleanable list.

The second command loads that exact plan. It accepts no flags that can expand
the target set.

### Advanced: cached-only review

```sh
car-go-clean run --dry-run --no-scan --all
```

This is useful when a current matching generation already exists. With only
historical path data, it returns `2`, creates no false authority, and invokes
no Cargo.

### Explicitly dynamic cleanup

```sh
car-go-clean run
```

Bare `run` scans and destructively cleans the fresh dynamic target set in one
operation. It is appropriate for an operator or daemon that intentionally
accepts that changing set. It is not the recommended interactive flow.

### Risk-bearing preview flags

| Flag | What it changes |
| --- | --- |
| `--include-managed-cache` | Allows protected managed/container targets that configuration already admitted. |
| `--include-active` | Allows a currently active project during plan creation. |
| `--force` | Bypasses scan-error, activity, and quiet-period gates during that operation. |

`--force` does not bypass scope, exclusions, direct readable target
requirements, same-device checks, identity checks, or the independent
managed-storage approval.

Reviewed execution carries the persisted managed-storage approval, but
rechecks current activity, scan errors, and quiet time strictly. The risky
preview flags are not a permanent waiver.

## 6. Running the daemon

Installing car-go-clean installs only the binary. The service is a separate,
explicit choice:

```sh
car-go-clean service install
car-go-clean service status
```

`service install` writes a per-user launchd definition on macOS or systemd
user unit on Linux, enables it, and starts it. No root service is installed.

The default schedule is:

- scan every 24 hours;
- clean every 24 hours; and
- require a two-hour target quiet period.

The next scan and clean timestamps live in the state database. A daemon
restart resumes that stored schedule instead of blindly waiting another full
interval.

The daemon reloads and validates the config at cycle boundaries. When the
current policy has no matching generation, it schedules a forced scan before
cleanup. Forced missing-generation attempts are limited to one every five
minutes. A failed scan records a retry and defers cleanup instead of using
stale authority.

### Persistent service states

Installed, enabled, and running are separate facts:

| Command | Persistent result |
| --- | --- |
| `service install` | Definition present, enabled, and running. |
| `service stop` | Definition retained, disabled, and stopped across login/reboot. |
| `service refresh` | Installed definition rewritten with current binary/physical roots and left disabled/stopped. |
| `service start` | Existing definition re-enabled and started. |
| `service restart` | Enabled service restarted; a disabled service is rejected. |
| `service uninstall` | Definition removed; config, state, logs, and history retained. |

On macOS, install explicitly clears launchd’s persistent disabled-database
entry before bootstrap. On Linux, running the user service after logout may
require `loginctl enable-linger "$USER"`; car-go-clean never changes that
account policy.

### Captured environment

The service definition captures supported manager-root variables so the
daemon and interactive shell build the same protected-root policy. `status`
and `health` report captured roots and warn when the current shell diverges.

After intentionally changing those roots, review them and run
`car-go-clean service stop`, then `car-go-clean service refresh`, to recapture
the environment while leaving the service disabled/stopped. Use
`service install` only when enabling and starting is intentional.

## 7. Understanding output

### Text and JSON

Text mode is for operators. `--json` provides a format-version-1 terminal
envelope containing:

- command and outcome;
- reasons;
- policy hash and generation where applicable;
- review ID where applicable;
- scan errors; and
- command-specific data.

Cleanup JSON is NDJSON. A `target` event appears immediately before each real
Cargo invocation, followed by one terminal envelope.

### Exit taxonomy

| Exit | Meaning | Operator response |
| --- | --- | --- |
| `0` | Complete coverage. | Inspect the result normally. |
| `2` | Structurally valid result with incomplete authority or discovery coverage. | Inspect origins, errors, policy, generation, and bounded targets. |
| `1` | Failure: config, state, lock, Cargo, measurement, or cleanup. | Stop and diagnose. |

`1` outranks `2` when both conditions occur.

Safety skips alone do not make the command fail. Common skip labels include:

- `no_target` and `active_recent_write`;
- `active_process`;
- `managed_cache` and `container_storage`;
- `scan_error` and `target_read_error`;
- `invalid_manifest`;
- unavailable or changed project/target identity;
- `cross_device_target`;
- `out_of_scope`; and
- `excluded`.

### macOS privacy

A broad macOS home scan can encounter TCC-protected directories. Incomplete
origins produce exit `2`; a bounded review ID may still exist for the paths
that were observed.

Do not treat `2` as blanket success. Inspect:

```sh
car-go-clean health --json
car-go-clean status --json
```

v0.4 excludes `~/Library` and `~/OrbStack` by default, but the default home
scan can still encounter protected locations such as Desktop or Documents.
For the most predictable privacy surface, narrow `scan_dirs` to the
directories that actually hold Rust work. Also check the actual binary
version, service state, effective config, and service-environment divergence;
an older running daemon or an override can have a broader policy.

## 8. Configuration tour

### Start with defaults

With no config file, car-go-clean scans `$HOME`, uses the protected exclusions
listed above, scans and cleans every 24 hours, and requires two hours of target
quiet.

The config path is:

```text
$XDG_CONFIG_HOME/car-go-clean/config.toml
# otherwise
$HOME/.config/car-go-clean/config.toml
```

An existing file is a strict optional overlay. Missing keys retain defaults.
Unknown keys fail.

### Make normal additions

Use `extra_excludes` to add exclusions without losing the maintained
platform defaults:

```toml
scan_dirs = ["~/src", "~/work"]
project_dirs = ["/opt/special-rust-project"]
extra_excludes = ["generated", "~/src/never-clean"]
clean_interval = "24h"
scan_interval = "12h"
target_quiet_period = "2h"
log_level = "info"
```

Paths support `~`, `$NAME`, and `${NAME}`. Scan and project roots must expand
to absolute paths. Relative exclusions match that component sequence wherever
it occurs; absolute exclusions stay anchored.

### Use overrides only deliberately

`override_excludes` replaces the editable default exclusion list.
`extra_excludes` is still added afterward.

This is how protected areas can become visible to discovery, so it should be
reviewed as a safety-policy change. Protected-storage cleanup still needs the
second `--include-managed-cache` gate.

### Migrate legacy v0.4 config

v0.4 still accepts legacy `excludes` as the advanced replacement form and
prints a deprecation warning. It is removed in v0.5.

```sh
car-go-clean config migrate
```

Migration validates the file, prints a key-only diff, and atomically renames
`excludes` to `override_excludes`. A file containing both keys is rejected.

### Inspect and round-trip

```sh
car-go-clean config
car-go-clean config > /absolute/path/effective-config.toml
```

The output is supported TOML that can be loaded again. It shows the effective
values without serializing internal provenance or authority state.

## 9. Safety tour

The normal safety boundary is layered rather than based on one “safe path”
test:

- **Direct files only.** `Cargo.toml` must be a direct regular file and
  `target/` a direct directory. Directory symlinks are not traversed.
- **Canonical scope.** The physical project must still be inside a configured
  scope and outside effective exclusions.
- **Same device.** Project and target must remain on the same filesystem
  device.
- **Identity.** Project and target objects must match the observed/reviewed
  identity, with boot-session-aware re-observation.
- **Quiet period.** The newest non-symlink target file must be old enough.
- **Activity.** A process whose current directory or command arguments point
  into the project/target causes a skip.
- **Discovery health.** Related unreadable paths and unresolved worktree
  discovery block cleanup.
- **Protected storage.** Package-manager and container roots have separate
  discovery and plan-time gates.
- **Final revalidation.** Every cleanable target passes the checks again
  immediately before Cargo.

Directory-size and newest-write walks ignore symlink entries rather than
following them. Cargo receives the exact direct target path through
`--target-dir`.

The model is fail-closed, not race-free. A filesystem can still change after
the last check and before Cargo acts; that residual TOCTOU window is stated
explicitly rather than disguised as a guarantee.

## 10. Data and accounting

The state directory is:

```text
$XDG_STATE_HOME/car-go-clean
# otherwise
$HOME/.local/state/car-go-clean
```

It contains:

- `state.db` — projects, generations, origins, observations, reviews, runs,
  clean events, errors, and scheduler state;
- `daemon.lock` — mutual exclusion for daemon and cleanup operations; and
- `car-go-clean.log` plus numbered rotations — daemon NDJSON logs.

Historical project rows answer reporting questions. Current generations and
observations answer authority questions. Schema migration retains useful
project, error, event, and recovery history but deliberately invalidates
path-only cleanup authority.

Every Cargo attempt records:

- project path and timestamp;
- measured bytes before and after;
- duration and exit code;
- a bounded stderr excerpt; and
- any measurement error.

Only exit-code-0 Cargo attempts contribute recovered bytes and successful
clean counts. Failed attempts are counted separately, appear through
`logs --errors-only`, and leave the project eligible for a later safe retry.

Useful views:

```sh
car-go-clean status
car-go-clean stats --since 1w --top 10
car-go-clean logs --errors-only --tail 100
```

## 11. Install, upgrade, rollback, uninstall

### Fresh install

The supported fresh-install methods are:

- Homebrew: `brew install dcchuck/tap/car-go-clean`
- the checksum-verifying GitHub Release shell installer.

Both install only the binary. Neither installs, enables, or starts the daemon.
The shell installer defaults to `$HOME/.local/bin` and does not edit `PATH`.

### Upgrade from v0.2 or v0.3

Do not replace a v0.2/v0.3 binary with plain `brew upgrade`, `brew install`, or
the ordinary installer. Use the released v0.4 two-phase upgrade helper.

Phase one:

1. verifies whether Homebrew or the shell install owns the visible binary;
2. records active, stopped, or absent service state;
3. persistently disables and stops every installed old definition through the
   native manager;
4. replaces the binary and disarms automatic old-service restoration;
5. verifies the exact v0.4 binary;
6. refreshes the installed definition and physical manager roots without
   enabling or starting it;
7. validates configuration; and
8. creates a reviewed dry-run plan while the service remains disabled.

Phase two executes only the supplied review ID while the service remains
disabled. After explicit approval and success, it re-enables and starts only a
service that was originally active. An originally stopped service remains
installed, disabled, and stopped. An absent service stays absent.

The legacy v0.2/v0.3 word **stopped** means “definition installed but process
observed inactive”; those versions do not report the separate enabled state.
The helper normalizes that installed legacy state to v0.4
`Installed: yes`, `Enabled: no`, `Running: no`, preventing manager recreation,
login, or reboot from resuming it during review.

The helper’s mode-0600 session binds the installation method, old state, exact
new binary path, phase, and review ID. Resume with the same method; do not
change `PATH` ownership mid-upgrade.

### Rollback and ambiguity

A failure before replacement may restore an originally active old service
because the exact old binary is still installed. As soon as replacement
succeeds, automatic old restoration is disarmed. A wrong replacement version
or any later pre-approval failure persists recovery state and leaves the
service disabled/stopped with exact rollback guidance.

After replacement, the helper fails closed. If review execution might have
started, inspect state and logs before retrying; do not repeat cleanup
blindly. If cleanup completed but service restoration failed, resuming the
same phase-two command performs restoration without cleaning twice.

Rollback validates the restored old version, restores the saved old
definition, reloads the manager where needed, and only then uses native
launchctl/systemd enable/bootstrap/start operations. v0.2/v0.3 do not
implement `service start`, so the helper never prints or invokes that verb
against those versions. Rollback and service uninstall leave config, database,
logs, reviews, and history intact.

Cross-method migration is deliberately not part of the helper. Explicitly
uninstall the old owner, then perform a fresh install with the new method.

### Uninstall

`car-go-clean service uninstall` removes only the per-user service definition.
It leaves config, database, logs, reviews, and history.

Removing the binary is package-manager-specific (`brew uninstall
car-go-clean`, or removing the known shell-owned binary). Data removal is a
separate, explicit operator decision.

## 12. Release pipeline

v0.4 uses a staged, commit-bound release rather than “push tag and hope.”

### Before the tag

1. Local verification runs formatting, clippy, tests, release scripts,
   cargo-dist planning, and release-note gates.
2. A manual rehearsal checks out an exact SHA and builds four archives:
   Apple Silicon macOS, Intel macOS, ARM64 Linux, and x86_64 Linux.
3. Each target verifies checksum, version, health, installer behavior, and
   formula rendering; macOS also installs/tests the local formula.
4. A tap-capability rehearsal creates a uniquely named public draft PR,
   verifies token permissions, closes that PR, and deletes only its branch.
5. The aggregate evidence binds SHA, version, runner/architecture, artifact
   hashes, outcomes, and immutable action pins.
6. Tart acceptance uses digest-pinned macOS and Linux guests, closed
   manifest-bound inputs, a real Rust project, reboot-aware service checks,
   strict config, exit taxonomy, Cargo failure, cached authority, and real
   v0.2/v0.3 upgrade fixtures.
7. Independent reviewers evaluate runtime safety, operator behavior, release
   workflows, evidence, and documentation.

No `v0.4.0` tag exists during those rehearsals.

### Publication

1. The owner explicitly authorizes an annotated `v0.4.0` tag for the exact
   reviewed commit.
2. The tag workflow creates or safely updates one commit-bound draft release.
3. The draft must contain an exact 15-file inventory: four archives, four
   archive checksums, four cargo-dist global assets, the installer, upgrade
   helper, and shell checksum manifest.
4. Authenticated verification checks the tag commit, assets, checksums,
   attestations, executable version/health, installer, no implicit service,
   and rendered formula.
5. The `v040-prerelease` protected environment requires human approval before
   publishing a non-latest prerelease.
6. Fresh hosted runners exercise the public, unauthenticated versioned assets.
7. The `v040-stable` environment requires a second approval before promoting
   that same release to stable/latest.
8. Only then does the workflow open/update a formula-only tap PR. It never
   pushes the tap default branch and never auto-merges the PR.

Transitions re-read the numeric release ID, tag commit, resolved target,
publication state, and asset inventory. Targeted retries cannot demote a
stable release or make an older stable release latest again.

The workflow does not publish to crates.io and does not enable a daemon.

## 13. Hands-on guided lab

Use an already installed v0.4 binary or `cargo build --locked` from this exact
checkout. Keep the lab under one disposable directory and use isolated config
and state paths.

### Create one disposable project

```sh
lab_root=$(mktemp -d "${TMPDIR:-/tmp}/car-go-clean-tour.XXXXXX")
cargo new --quiet "$lab_root/sample"
cargo build --manifest-path "$lab_root/sample/Cargo.toml"
lab_config="$lab_root/config.toml"
lab_state="$lab_root/state"
printf 'scan_dirs = ["%s"]\ntarget_quiet_period = "1s"\n' \
  "$lab_root" > "$lab_config"
sleep 2
test -d "$lab_root/sample/target"
```

### Inspect before acting

```sh
car-go-clean version
car-go-clean service status
car-go-clean health --config "$lab_config" --state-dir "$lab_state" || \
  test $? -eq 2
car-go-clean config --config "$lab_config"
```

An empty state has no discovery generation yet, so the first health check may
return `2`. That is the expected distinction between valid configuration and
current cleanup authority.

### Create and execute an exact review

```sh
set +e
preview_output=$(
  car-go-clean run --dry-run --all \
    --config "$lab_config" \
    --state-dir "$lab_state"
)
preview_status=$?
set -e
printf '%s\n' "$preview_output"
case "$preview_status" in 0|2) ;; *) exit "$preview_status" ;; esac
review_id=$(
  printf '%s\n' "$preview_output" |
    sed -n 's/^Review ID: \([0-9][0-9]*\)$/\1/p'
)
test -n "$review_id"
test -d "$lab_root/sample/target"
```

Then execute only that ID and inspect accounting:

```sh
car-go-clean run --review "$review_id" --json \
  --config "$lab_config" \
  --state-dir "$lab_state"
test ! -d "$lab_root/sample/target"
car-go-clean status --json \
  --config "$lab_config" \
  --state-dir "$lab_state"
car-go-clean stats --json --state-dir "$lab_state"
car-go-clean logs --errors-only --json --state-dir "$lab_state"
```

### Compare the dynamic path inside the fixture

This is deliberately safe only because the scope contains one disposable
project:

```sh
cargo build --manifest-path "$lab_root/sample/Cargo.toml"
sleep 2
car-go-clean run \
  --config "$lab_config" \
  --state-dir "$lab_state"
test ! -d "$lab_root/sample/target"
```

Rebuild once and inspect explicit discovery plus cached-only review:

```sh
cargo build --manifest-path "$lab_root/sample/Cargo.toml"
sleep 2
car-go-clean scan --json \
  --config "$lab_config" \
  --state-dir "$lab_state"
car-go-clean projects --all --json \
  --config "$lab_config" \
  --state-dir "$lab_state"
car-go-clean run --dry-run --no-scan --all --json \
  --config "$lab_config" \
  --state-dir "$lab_state"
```

### Exercise service lifecycle only in a disposable VM

Service commands are user-manager operations, not confined by `lab_root`.
Run this part only in a throwaway VM with no existing car-go-clean service:

```sh
car-go-clean service install
car-go-clean service status
car-go-clean service stop
car-go-clean service refresh
car-go-clean service start
car-go-clean service restart
car-go-clean service uninstall
car-go-clean service status
```

The repository’s executable packaging test runs the same command surface
against an isolated fake user manager. The release-acceptance harness runs the
real lifecycle, including persistent stop across a guest reboot, on both
macOS and Linux.

## 14. Troubleshooting map

| Symptom | What it usually means | First checks |
| --- | --- | --- |
| macOS directory prompts or TCC errors | The default broad home root, an override, or an older daemon reached privacy-protected paths. | `version`, `service status`, `config`, then `health --json`; narrow `scan_dirs` to actual Rust roots. |
| Exit `2` | Output is valid, but discovery/generation coverage is incomplete. | Inspect `outcome.reasons`, `scan_errors`, `incomplete_origins`, policy hash, and generation. |
| Exit `1` with `lock_unavailable` | The daemon or another one-shot command owns the state lock. | Check `service status`; do not delete the lock or race the active process. |
| Review missing or expired | ID is absent, older than 30 minutes, or pruned. | Create a new dry run and inspect it again. |
| Review policy/generation mismatch | Config, protected-root environment, scope, exclusions, or discovery changed. | Do not force the old ID; create a new review. |
| Project skipped as active/recent | A process refers to it or target files are inside the quiet period. | Stop the build/process or wait; use risky flags only after explicit review. |
| Managed/container project absent | Defaults excluded it before discovery. | Prefer leaving it protected. Admission requires reviewed `override_excludes` plus plan-time managed approval. |
| Service says installed but not enabled/running | It was persistently stopped, or manager state diverged. | Use `service status`; run `service start` only when background operation is intended. |
| Service environment divergence | Shell and installed definition resolve protected roots differently. | Review the roots, then `service install` to recapture. |
| Legacy `excludes` warning | v0.4 compatibility key remains in config. | Run `config migrate`; resolve an `excludes`/`override_excludes` conflict manually. |
| Cargo clean failed | Cargo returned nonzero; no successful recovery is credited. | `logs --errors-only`, `stats`, and the recorded stderr excerpt. |
| Shell install command not found | Installer wrote `$HOME/.local/bin` but did not edit `PATH`. | Export that directory, refresh the shell command cache, and re-run `command -v`. |
| Linux daemon stops after logout | User-manager lingering is not enabled. | Decide whether account-level linger is desired; car-go-clean will not enable it. |

## 15. What remains deliberately manual

Automation stops at decisions that materially change authority or public
state:

- A human or explicitly authorized agent chooses whether to execute a dry-run
  review.
- `--force`, `--include-active`, and `--include-managed-cache` require an
  operator to accept the named risk.
- Service installation, persistent stop/start, and Linux account lingering
  are explicit choices.
- Cross-method installation migration and removal of retained config/state are
  not inferred.
- The owner authorizes the exact annotated release tag only after the full
  readiness evidence is reviewed.
- Protected environments require separate prerelease and stable approvals.
- The Homebrew tap PR is inspected and merged manually.

These are product boundaries, not missing automation.
