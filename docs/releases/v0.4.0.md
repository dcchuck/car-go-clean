# car-go-clean v0.4.0

## What changed

- Every dry run persists a 30-minute review plan bound to the exact cleanup
  policy and discovery generation. At most 20 current plans are retained.
- `run --review ID` executes only persisted targets. Final revalidation can
  remove a target that became unsafe and can never add a newly eligible one.
- Bare `run` remains a dynamic destructive operation for operators who
  intentionally accept a freshly discovered target set. `--all` is
  display-only and requires `--dry-run`.
- Cached paths are history, not authority. `--no-scan` never bypasses policy,
  generation, scope, exclusion, identity, activity, quiet-period,
  scan-coverage, or managed-storage checks.
- Managed storage has two gates: configuration must admit it into discovery,
  and plan creation must explicitly use `--include-managed-cache`. Reviewed
  execution carries only that persisted approval.
- Project and target filesystem identity is revalidated immediately before
  Cargo. This narrows, but cannot eliminate, the residual
  time-of-check/time-of-use window.
- Machine output uses format version 1. Cleanup execution is NDJSON with a
  `target` event before each Cargo invocation and one terminal envelope.
- Stable exits are `0` complete, `2` valid but incomplete, and `1` failed;
  `1` outranks `2`. A normal macOS privacy/TCC denial can produce `2` while a
  bounded review still exists.
- Service definitions now distinguish installed, enabled, and running state,
  capture supported policy-root environment, and report recapture divergence.
  Service warnings are diagnostic and do not alter cleanup authority.
- `service stop` persists across login/reboot, `service start` re-enables, and
  `service uninstall` removes only the definition while retaining config and
  state.

The binary installation paths still do not install, enable, or start a daemon.

## Recommended manual cleanup

```sh
car-go-clean run --dry-run --all
car-go-clean run --review REVIEW_ID
```

Replace `REVIEW_ID` with the ID printed by the first command. The plan expires
after 30 minutes and is rejected after a policy or discovery-generation
change.

## v0.2/v0.3 upgrade helper

Use the released helper for a state-preserving upgrade. Download it and the
shared checksum inventory into an empty directory:

```sh
curl --proto '=https' --tlsv1.2 -fsSLO \
  https://github.com/dcchuck/car-go-clean/releases/download/v0.4.0/car-go-clean-upgrade.sh
curl --proto '=https' --tlsv1.2 -fsSLO \
  https://github.com/dcchuck/car-go-clean/releases/download/v0.4.0/car-go-clean-shell-assets.sha256
awk '$2 == "car-go-clean-upgrade.sh" { print }' \
  car-go-clean-shell-assets.sha256 > car-go-clean-upgrade.sha256
if command -v sha256sum >/dev/null 2>&1
then
  sha256sum -c car-go-clean-upgrade.sha256
else
  shasum -a 256 -c car-go-clean-upgrade.sha256
fi
chmod +x car-go-clean-upgrade.sh
```

Start phase one with the method that owns the existing command returned by
`command -v car-go-clean`:

```sh
./car-go-clean-upgrade.sh --version 0.4.0 --method homebrew
# or:
./car-go-clean-upgrade.sh --version 0.4.0 --method shell
```

The helper verifies ownership before stopping a service or replacing anything.
`homebrew` requires the visible command to resolve to the installed formula's
exact binary; `shell` requires a writable, absolute, non-symlink shell
installation and rejects a Homebrew-managed command. The existence of some
Homebrew formula is not enough when a shell installation shadows it on
`PATH`. Deliberate cross-method migration is unsupported by this v0.4 helper:
uninstall the old method and perform a separate fresh install instead.

The helper accepts exactly v0.2.0 or v0.3.0 when an old binary is present,
records whether its service was active, stopped, or absent, and uses the
native service manager to stop an active old daemon before replacement. A
stopped service remains stopped and an absent service remains absent. A
failure before exact v0.4.0 replacement restores only a service that was
originally active.

After replacement, the helper resolves and validates the exact v0.4.0 binary
path, then uses that path for config and `run --dry-run --all`. Preview exit
`0` and `2` are valid; exit `1` stops the upgrade and prints recovery/rollback
guidance. The mode-0600 session persists that absolute binary path with the
method, old state, phase, and review ID. Re-running the same phase-one command
therefore resumes an interrupted preview without replacing the binary or
re-resolving a different command through `PATH`.

Inspect the complete preview and its incomplete origins. Then execute the
exact ID printed by the helper:

```sh
./car-go-clean-upgrade.sh \
  --version 0.4.0 \
  --method homebrew \
  --execute-review REVIEW_ID
```

Use exactly the same ownership method in phase two. Reviewed exits `0` and `2`
are accepted, and version validation plus reviewed execution use the exact
path persisted in phase one even if `PATH` or a shell command cache changes.
After success, only an originally active service is restored. If execution may
have begun but did not finish, the helper fails closed with an `executing`
session and tells you to inspect state and logs; do not repeat cleanup blindly.
If cleanup completed but service restoration failed, resume the same
`--execute-review` command to finish restoration without cleaning twice.

## Configuration migration

The legacy `excludes` key still loads in v0.4 with a deprecation warning and
the advanced replacement semantics of `override_excludes`. It is removed in
v0.5. There is no date-based promise; migrate before that version:

```sh
car-go-clean config migrate
# or:
car-go-clean config migrate --config /absolute/path/config.toml
```

Migration validates the config, shows a key-only diff, and atomically rewrites
that file. A conflict between `excludes` and `override_excludes` is rejected.

## Service operation

`car-go-clean service install` writes, enables, and starts the per-user
definition and captures supported cleanup-root environment. `stop` disables
and stops persistently; `start` re-enables and starts. `uninstall` removes the
definition only and retains config, state, logs, and history.

On Linux, running a user service after logout may require an explicit account
policy change. car-go-clean never performs it:

```sh
loginctl enable-linger "$USER"
```

## Release compatibility gate

The repository toolchain and `Cargo.toml` minimum supported Rust version are
both Rust 1.95. The executable `tests/msrv.sh` gate prevents those declarations
from drifting apart.
