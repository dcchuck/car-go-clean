# car-go-clean v0.4.3

## Improvements

- Leave truly empty target directories untouched without invoking Cargo. Empty
  container mountpoints no longer generate repeated missing-marker failures.
  A zero-byte file or symlink is still an entry, not an empty target.
- Pin Cargo's `build.build-dir` to the same reviewed target as `--target-dir`,
  preventing a separately configured intermediate directory from being cleaned.
- `projects` reports advisory cache-tag warnings for nonempty eligible workspace
  targets without modifying markers or changing eligibility.
- `health` and `status` report last unresolved cleanup failures, consecutive
  attempts, recorded remaining bytes, stderr (JSON), and remediation. These are
  advisory diagnostics; existing command outcomes and exit codes are unchanged.
- Failed or incomplete daemon cycles log at WARN, with existing structured
  counters. The normal project summary lists the largest skipped targets and
  their reasons.

## Safety and compatibility

Discovery is unchanged: scanning stops at the first Cargo manifest. Nested
projects are not newly admitted automatically, even if they have their own
targets. Active-process and quiet-period protections are unchanged.

Cargo's marker validation is preserved. This release does not create or repair
`CACHEDIR.TAG`, remove the explicit target argument, or fall back to recursive
filesystem deletion. Untagged nonempty targets may still fail. See
[cleanup diagnostics](../cleanup-diagnostics.md).

Paths containing `{` or `}` are refused at execution because Cargo expands
templates in `build-dir`; they cannot safely be passed as literal paths.

Configuration keys and the database schema are unchanged. Legacy `excludes`
remains an exact replacement alias for `override_excludes`, with its existing
warning; `config migrate` previews the rename and requires its explicit apply
option. Defaults, including protected container/managed storage, are unchanged.
No automatic config migration occurs. Existing v0.4 state remains readable.

JSON additions are additive under format version 1. `health` and `status`
continue to base their outcomes on discovery/authority health; historical cleanup
failures do not change their exit codes. A complete outcome is not a claim that
all previous cleanup attempts succeeded. Old failure records
are intentionally not erased by an empty skip or the passage of 24 hours;
recorded bytes are not a live disk measurement. A later successful measured
attempt for that path resets the consecutive-failure sequence.

For a future approved upgrade, back up state/config/service, stop the daemon,
install the selected release, and obtain a fresh scan and dry-run review before
re-enabling scheduled cleanup.
Do not reuse pre-upgrade review plans. The v0.2/v0.3 helper is specifically for
its documented v0.4 transition; do not substitute 0.4.3 into that helper.

## Release gate

This is a prepared candidate, not a published release. macOS validation and
remaining limitations are recorded in the local investigation assessment.
Linux CI, signed/attested packaging, installation/upgrade rehearsal, and owner
approval remain required before publishing or upgrading a running service.
